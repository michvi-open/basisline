# Basisline

**An open specification for preserving the evidence, assumptions, and outcomes behind important business decisions.**

No account. No proprietary database. No vendor lock-in.

> Basisline does not tell you what decision to make. It preserves what made the decision reasonable at the time.

**Preserve the basis of the decision.**

---

## 1. What Basisline Is

Basisline is a **specification**, not a product.

It defines a small, portable file format — a **Decision Receipt** — that captures why a decision was made, what it was based on, and allows its later outcome to be linked without altering the original record.

A reference implementation (a simple local form) exists to make receipts easy to create. But the specification is the canonical asset. Anyone can build a tool that reads or writes Basisline receipts, the same way anyone can build a tool that reads or writes Markdown.

```
Specification (canonical)
        ↓
Reference implementation (this repo's form/generator)
        ↓
Future tools (compatible ecosystem — not owned by anyone)
```

## 2. The Problem

Every organization makes consequential decisions — budget changes, vendor approvals, campaign pauses, payment releases. Months later, someone asks: *"Why did we do this?"*

The decision is remembered. The evidence behind it almost never is. It lives in a Slack thread, a dashboard screenshot, someone's memory — and all of it degrades or disappears.

Poor decisions are not always caused by bad data. Sometimes the evidence was reasonable at the time, but the **assumptions surrounding it later changed or proved incorrect** — and nobody had a record of what those assumptions were.

## 3. Core Philosophy

- **Open** — anyone can implement the spec.
- **Portable** — a receipt is a file. Git, Notion, a folder, a USB drive — it doesn't matter.
- **No lock-in** — no account, no cloud dependency, no proprietary storage.
- **Human-readable first** — a non-technical founder or CFO should understand a receipt in 30 seconds.
- **Machine-readable second** — the same file is valid JSON, so tools can parse it.

## 4. Two Record Types

Basisline defines two immutable record types, kept deliberately separate:

```
Decision Receipt:   Evidence → Assumptions → Decision
Outcome Record:     Decision Receipt → Outcome → Learning
```

A Decision Receipt is written once, at decision time, and never edited. When the outcome becomes known — 30 days later, 6 months later — a **separate** Outcome Record is created that references the receipt. The original receipt stays untouched, exactly as it was at the moment of the decision.

### 4.1 Decision Receipt — Field Reference (v0.1)

| Field | Type | Required | Description |
|---|---|---|---|
| `basisline_version` | string | yes | Spec version this record conforms to |
| `record_type` | string (`"receipt"`) | yes | Identifies this as a Decision Receipt |
| `receipt_id` | string | yes | Unique identifier |
| `decision.summary` | string | yes | One-line description of what was decided |
| `decision.context` | string | yes | Where/why this decision exists (e.g. the broader initiative it belongs to) |
| `decision.owner` | string | yes | Person or role accountable for the decision |
| `decision.date` | date | yes | When the decision was made |
| `decision.confidence` | enum (`low`/`medium`/`high`) | yes | Owner's stated confidence at the time |
| `evidence` | array | yes | List of `{source, metric, value, unit, freshness_days}` objects |
| `evidence_as_of` | datetime | yes | The point in time the evidence was considered valid |
| `assumptions` | array of strings | yes | What had to be true for this decision to make sense |
| `known_conflicts` | array of strings | no | Contradictions or discrepancies known at decision time |
| `review_after_days` | integer | yes | When this decision should be revisited |
| `revision.supersedes` | string or null | no | `receipt_id` of an earlier receipt this one replaces |
| `revision.related_receipt_ids` | array | no | Other loosely related receipts |

### 4.2 Outcome Record — Field Reference (v0.1)

| Field | Type | Required | Description |
|---|---|---|---|
| `basisline_version` | string | yes | Spec version this record conforms to |
| `record_type` | string (`"outcome"`) | yes | Identifies this as an Outcome Record |
| `outcome_id` | string | yes | Unique identifier |
| `receipt_id` | string | yes | The Decision Receipt this outcome belongs to |
| `recorded_on` | date | yes | When the outcome was logged |
| `actual_result` | string | yes | What actually happened |
| `learning` | string | yes | What this reveals for future decisions |

### 4.3 Example: Decision Receipt

```json
{
  "basisline_version": "0.1",
  "record_type": "receipt",
  "receipt_id": "bl_2026-08-20_a91f",
  "decision": {
    "summary": "Increase Google Ads budget by ₹5 lakh",
    "context": "Marketing budget allocation for Q3 2026",
    "owner": "Marketing Head",
    "date": "2026-08-20",
    "confidence": "medium"
  },
  "evidence": [
    { "source": "GA4", "metric": "leads", "value": 420, "unit": "count", "freshness_days": 2 },
    { "source": "CRM", "metric": "qualified_leads", "value": 61, "unit": "count", "freshness_days": 1 },
    { "source": "Finance", "metric": "recognized_revenue", "value": 1820000, "unit": "INR", "freshness_days": 5 }
  ],
  "evidence_as_of": "2026-08-20T10:00:00Z",
  "assumptions": [
    "CRM-qualified lead rate stays consistent with the last 60 days",
    "Ad platform attribution roughly reflects real conversions"
  ],
  "known_conflicts": [
    "Google Ads platform attributed 690 conversions — 570% higher than CRM-qualified count"
  ],
  "review_after_days": 30,
  "revision": {
    "supersedes": null,
    "related_receipt_ids": []
  }
}
```

`value` and `unit` are kept separate and typed (numbers, not display strings) so tools can compute with them. A Markdown renderer is responsible for formatting `1820000 INR` as `₹18.2L` for human display — the raw record stays machine-safe.

### 4.4 Example: Outcome Record

```json
{
  "basisline_version": "0.1",
  "record_type": "outcome",
  "outcome_id": "bo_2026-09-20_b12c",
  "receipt_id": "bl_2026-08-20_a91f",
  "recorded_on": "2026-09-20",
  "actual_result": "Recognised revenue was ₹11.4 lakh",
  "learning": "Platform attribution materially overstated CRM-confirmed commercial outcomes"
}
```

### 4.5 Human-Readable (Markdown) Rendering

Every record can also render as plain Markdown. A receipt and its outcome render as linked but separate blocks:

```markdown
## Decision: Increase Google Ads budget by ₹5 lakh
**Context:** Marketing budget allocation for Q3 2026
**Owner:** Marketing Head · **Date:** 2026-08-20 · **Confidence:** Medium

**Evidence (as of 2026-08-20):**
- GA4 leads: 420
- CRM qualified leads: 61
- Finance recognised revenue: ₹18.2L

**Assumptions:**
- CRM-qualified lead rate stays consistent with the last 60 days
- Ad platform attribution roughly reflects real conversions

**Known conflict:** Google Ads platform attributed 690 conversions — 570% higher than CRM-qualified count.

**Review after:** 30 days

---
### Outcome — recorded 2026-09-20
**Result:** Recognised revenue was ₹11.4 lakh
**Learning:** Platform attribution materially overstated CRM-confirmed commercial outcomes
```

## 5. Immutability & Revision

Both record types are **immutable once created** — never edited in place, only added to.

- An outcome is never written back into a receipt. It is always a new, separate Outcome Record that references the receipt by `receipt_id`.
- If a decision itself is revised (not just its outcome), a **new** Decision Receipt is created with `revision.supersedes` pointing to the original. The old receipt is left untouched.

```
Receipt A  ──── superseded by ────▶  Receipt B
   │
   └──▶ Outcome Record (references Receipt A directly, unaffected by later revisions)
```

This keeps an honest history of how both the decision and the thinking behind it evolved, rather than a single rewritten "final" version.

## 6. Non-Goals (v0.1)

Basisline is explicitly **not**:

- An analytics tool
- A CRM or finance system
- A dashboard or BI product
- A cloud service with accounts or billing
- An AI decision-recommendation engine

If any of these are wanted later, they belong in a separate tool built *on top of* the spec — not inside it.

## 7. Reference Implementation Scope (v0.1)

Kept deliberately lean:

1. JSON Schema (formal, for validation of both record types)
2. Markdown renderer (receipt or outcome → human-readable doc)
3. A local web form (no login, no server-side storage — writes files locally)
4. Receipt generator (form → `.json` + `.md` Decision Receipt)
5. Outcome recorder (form → new, separate `.json` + `.md` Outcome Record linked by `receipt_id`)
6. Five example receipt/outcome pairs, covering different decision types
7. This documentation

No dashboard. No notifications. No database. No analytics integration.

If people genuinely use this, the next layer gets built in response to real usage — not in anticipation of it.

### 7.1 Repository Structure

```
spec/            — the specification itself (this document + versioned changes)
schema/          — JSON Schema files for validation
examples/        — sample receipt/outcome pairs
renderer/        — record → Markdown rendering logic
reference-app/   — the minimal local form + generator
tests/           — schema and renderer tests
CONTRIBUTING.md
LICENSE
```

The code stays intentionally small. The structure is what should read as disciplined — a spec, a schema, examples, and a thin reference layer, with no proprietary logic mixed in.
